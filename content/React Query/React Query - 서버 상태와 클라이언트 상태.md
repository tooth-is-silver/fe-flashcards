# React Query - 서버 상태와 클라이언트 상태

## 질문

서버 상태와 클라이언트 상태는 어떻게 구분하나요? 왜 서버 상태에는 캐시와 재검증이 필요한가요?

## 최적 답변

둘을 가르는 기준은 소유권입니다. 원본이 서버에 있고 클라이언트에는 사본만 있는 데이터가 서버 상태이고, 클라이언트에서 생겨 클라이언트에서 끝나는 값이 클라이언트 상태입니다. 모달이 열렸는지, 폼에 무엇을 입력했는지는 서버가 알 필요가 없습니다.

사본이라는 성질에서 문제가 따라옵니다. 원본은 다른 사용자의 요청이나 배치 작업으로 언제든 바뀌므로 사본은 시간이 지나면 원본과 어긋납니다. 그래서 서버 상태에는 캐시, 만료 판단, 재검증, 같은 요청 중복 제거, 화면을 떠날 때의 요청 취소, 실패 시 재시도가 필요합니다. 리덕스 사가로 서버 데이터를 다루면 이 장치들을 액션·리듀서·핸들러로 API마다 직접 만들게 되고, 이것이 보일러플레이트의 실체입니다. 리액트 쿼리로 옮기면 같은 장치가 쿼리 키를 기준으로 기본 제공되고, 갱신 후에는 키로 무효화만 하면 됩니다.

남은 클라이언트 상태는 성질에 따라 자리를 나눕니다. 링크 공유나 뒤로가기가 필요하면 URL 쿼리 파라미터, 한 서브트리에서만 공유하면 컨텍스트, 앱 전반에서 쓰면 전역 스토어, 그 외에는 컴포넌트 로컬입니다. 전역 스토어에서 서버 데이터가 빠지면 전역 상태가 작아지고, 어떤 화면이 어떤 데이터를 쓰는지가 쿼리 키로 드러나 수정 범위가 키 단위로 좁혀집니다.

## 반드시 포함할 키워드

- 구분 기준은 소유권
- 서버 상태는 사본
- 사본이라 원본과 어긋남
- 캐시·재검증·중복제거·취소·재시도
- 남은 클라 상태는 URL·컨텍스트·전역·로컬로 분류

## 자주 틀리는 표현

- 서버에서 온 데이터도 전역 스토어에 넣어 관리하면 된다.
- 모달 개폐나 폼 입력값도 서버 상태로 봐야 한다.

## 한 줄 요약

소유권으로 갈라 서버에 원본이 있는 사본이 서버 상태이고, 사본이라 원본과 어긋나므로 캐시·재검증·중복제거가 필요하며, 남은 클라이언트 상태는 URL·컨텍스트·전역·로컬로 나눈다.

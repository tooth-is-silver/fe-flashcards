# Monitoring - 로그 상관관계와 분산 추적

## 질문

프론트에서 발생한 에러와 백엔드 로그를 어떻게 연결하나요? 발생 시각으로 맞추면 왜 어긋나나요?

## 최적 답변

시각으로 맞추는 방식이 어긋나는 이유는 두 가지입니다. 클라이언트 시계는 서버와 다르게 흐르고, 트래픽이 몰리면 같은 초에 같은 엔드포인트에서 같은 상태 코드가 여러 건 나와 어느 사용자의 요청인지 특정할 수 없습니다.

그래서 요청마다 고유한 아이디를 만들어 양쪽 로그에 같이 남깁니다. 프론트가 요청을 보낼 때 아이디를 헤더에 실어 보내고, 서버는 그 값을 자기 로그에 기록합니다. 프론트에서 에러를 캡처할 때 같은 아이디를 태그로 붙이면 서버 로그에서 그 값으로 바로 검색됩니다. 헤더 이름을 임의로 정하는 대신 W3C 트레이스 컨텍스트의 `traceparent`를 쓰면 중간의 게이트웨이나 로깅 도구가 알아서 이어받습니다.

반대 방향도 있습니다. 서버가 응답 헤더로 자기 요청 아이디를 내려주는 방식입니다. 실패 응답에서도 헤더는 읽을 수 있으므로 에러 리포트에 그 값을 담고, 사용자가 CS로 문의할 때 화면에 이 아이디를 보여주면 문의 한 건을 로그 한 건으로 바로 연결합니다. 분산 추적을 켜면 프론트에서 만든 스팬과 서버 스팬이 같은 트레이스로 묶여 어느 구간에서 시간이 걸렸는지까지 한 화면에서 보이므로, 간헐적 타임아웃처럼 재현이 어려운 문제의 원인 구간을 좁힐 수 있습니다.

## 반드시 포함할 키워드

- 시각 매칭은 시계 차이·동시 요청으로 어긋남
- 요청 고유 아이디를 양쪽 로그에
- W3C traceparent 표준 헤더
- 응답 헤더로 request id 내려주기(CS 연결)
- 분산 추적으로 스팬을 트레이스로 묶기

## 자주 틀리는 표현

- 타임스탬프만 맞추면 프론트·백엔드 로그를 정확히 연결할 수 있다.
- 실패(4xx·5xx) 응답에서는 헤더를 읽을 수 없다.

## 한 줄 요약

시각 매칭은 시계 차이·동시 요청으로 어긋나므로, 요청마다 고유 아이디(W3C traceparent)를 양쪽 로그에 남기거나 서버가 응답 헤더로 내려주고, 분산 추적으로 스팬을 묶어 원인 구간을 좁힌다.
